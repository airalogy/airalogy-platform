# Airalogy Platform v0.5.0-beta.1

This beta is for deliberately selected internal evaluation. It collects the R&D workbench, research documents, organization navigation and research-tool changes since v0.4.1. It is not a stable release or evidence that any instance has been upgraded. The release package contains the full changes in `CHANGELOG.md`.

## Research work and navigation

- Project work items support requirements, tasks, issues and milestones, with assignment, dependencies, lists, boards and planned timelines. Discussion, decisions, evidence, tests and acceptance have separate records, revision conflicts and local draft recovery. A Protocol is not required first.
- Documents support daily notes, meetings and proposals, with templates, autosave, occurrence dates, materials and result snapshots. Home resumes recent work. Saved templates exclude measured values and attachments; personal documents retain their access boundaries.
- Organizations support company, institution and laboratory types. Single-organization deployments use short project URLs and `/organization`; multi-organization deployments use `/orgs`. Legacy `/labs` browser links remain compatible. Existing project names, asset IDs and access permissions are preserved.
- Single-organization profiles show actual membership and role instead of redundant organization counts/lists. Profile, setup, sign-in and project-menu translations are improved, alongside narrow-screen search and filtering.

## Protocols, Records and research tools

- Protocol editing and Record entry use the native AIMD Recorder, with per-field Aira review, local drafts and separate example previews. Fixes preserve ZIP root files and the last visual document edit before saving.
- Protocol ratings are version-specific, with optional use feedback and permission-aware adoption metrics. Aira communication preferences require explicit save/forget requests; automatic habit inference is not included.
- External research tools can use separately authorized immutable snapshots, private analysis reports and candidate methods. Writes and candidate Protocol publication retain browser confirmation. Existing tokens do not gain scopes automatically, and historical Record versions remain available.
- Self-hosted onboarding videos include Chinese/English captions and explicitly synthetic examples. Real-model Aira actions need separately configured services; basic R&D management remains available without AI.

## Identity and delivery

The product, Web and image version is `0.5.0-beta.1`; Python packages use the equivalent `0.5.0b1`, and the Git tag is `v0.5.0-beta.1`. Exact-commit source CI, provenance/digest verification, artifact acceptance, recovery and upgrade gates remain mandatory. GitHub marks the release as a prerelease, does not select it as Latest, and stable image aliases remain unchanged. Private operational files are excluded from Git and build contexts.

Publication and deployment are separate actions. Select a complete verified release package and record its version, full Git SHA, manifest digest and image digests. A version label alone does not identify the code actually running on an instance.

## Upgrade and acceptance

Upgrading from the official v0.4.1 traverses eight migrations, `0079_research_documents` through `0086_project_work`, covering documents, templates, visit history, external research, ratings, Aira preferences, organizations and work items. Development instances must start from their actual schema and source revision. An instance already at `0086_project_work` still requires migration-content and configuration checks; comparing footer versions is insufficient.

1. Follow [Release and Deployment Identity](../release-and-deployment-identity.md), verify recovery points for the database, referenced files, configuration and corresponding artifacts, and rehearse the actual source-to-target upgrade.
2. Use isolated test assets to verify login/access, legacy URLs, document save/reload, work items and discussion, Protocol editing and Record submission. Check basic workflows with AI disabled.
3. Schedule any required write pause, install the same immutable artifacts that passed acceptance, and verify runtime identity, health and affected user tasks.
4. Define rollback triggers and treatment of writes after cutover. Switching application images does not reverse database migrations; do not automatically overwrite the database or discard new data.

Beta acceptance does not qualify physical instruments and does not add SSO, multi-node high availability or regulatory certification. These notes do not replace instance-specific acceptance and recovery records.
