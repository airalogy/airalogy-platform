# Project meetings and research activity

A meeting is a project-owned specialization of one ResearchDocument/ResearchLogEntry. The existing entry remains the sole owner of title, AIMD body, actual occurrence time and revision. One meeting is one activity; edits and participant changes do not add activity counts. Planned/cancelled meetings are excluded from occurred activity. Scheduling is optional; recording a completed meeting is the default.

Meeting participants are historical attendance facts, not access grants. Account references retain display-name snapshots; external people may be recorded without accounts. Audience is either authorized project readers or selected authorized project members. The author manages audience; explicit editors can revise, commenters can comment, and project permissions are always rechecked. No project membership or external invitations are created implicitly. Restricted meeting access applies to document reads, history, browsing/counts, source selection and work evidence. Existing project files keep their own audience; a meeting reference never changes file permissions.

Meeting work links reference existing ProjectWork/ResearchTask identities, with origin/review semantics and the exact meeting revision. Creating an action and linking it is one transaction with a persistent retry key. Work titles and states are read live; historical meeting text and work evidence remain versioned. A restricted meeting can originate a project-visible work item only through an explicit UI action explaining that audience; the meeting body is never copied into the task.

The activity summary and timeline use the same authorized event query, category, actor and local-calendar date boundaries. Counts cover the complete result, independent of pagination. Record/Protocol/Knowledge permissions are enforced before counting. Meeting documents are not double counted. Material revisions remain in their own source history; autosave is not an extra research event.

First delivery includes project meeting list/detail, recording/optional preparation, account/external participants, audience, minutes, comments, task create/link and project overview activity plus full timeline. Recurring scheduling, notifications, external sharing, real-time collaborative text and transcription are future work.

Migration 0087 adds meeting metadata/participant/access/comment/work-link tables without changing existing research content. A populated downgrade is forbidden. Deployment must rehearse 0086 -> 0087 on an independently restored source database. Old application revisions do not enforce meeting ACL: rollback to a pre-meeting application is allowed only before any meeting exists; after writes, use a verified meeting-aware recovery build or forward fix, never restore over new writes automatically.

## Project people and atomic action batches

`ProjectPerson` is a reusable, project-scoped contact with an optional account association. It does not create a User, LabUser, ProjectUser or meeting audience entry. Writers may record names; only project administrators may associate or reassociate an account. The account must already have project access. Names are not unique identifiers and are never merged automatically. Association changes record actor, time, prior/new account and revision. One account can be associated with at most one contact within a project. Historical participant names and work revision snapshots are retained.

Work retains existing account assignments and additionally supports a responsible contact and contact collaborators. `mine` includes direct account assignments and contacts currently associated with that account, then applies current project permissions. Revoking access hides those tasks again without rewriting history. A timing note preserves relative requirements without inventing a calendar date.

`POST /meetings/with-actions` creates minutes and up to 50 action rows in one transaction. `POST /meetings/{id}/actions/batch` creates and/or links existing work at an exact saved revision. A stable batch UUID, actor and content digest make repeated calls idempotent; changed reuse conflicts. Any invalid row rolls back the entire batch. Each action remains one canonical ResearchTask and links the source meeting revision. An explicit action title/goal is project-visible; the service never copies private meeting text into task content.

Migration `0088_project_people` is additive and does not infer contacts from old free-text minutes or rewrite existing tasks. It also stores participant order. A downgrade refuses to discard populated people, batch receipts, participant order or timing notes. Deploy only after rehearsing the actual 0087-to-0088 transition and confirming a recoverable backup. After using the new fields, recovery requires a build that understands them; switching images is not a database rollback.
